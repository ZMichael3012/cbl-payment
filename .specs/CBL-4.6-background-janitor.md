# CBL-4.6. Фоновые задачи: истечение счетов и зависшие платежи

| Поле | Значение |
| :-- | :-- |
| Эпик | E4, Payment Service |
| Репозиторий | `cbl-payment` |
| Размер | M |
| Волна и параллельная группа | W2-PAYMENT |
| Зависит от | 4.1, предикат `ShouldExpire` из 4.5 |
| Версия контрактов | `cbl-protos@cf-2` (новых контрактов нет) |
| Статус | done, ревью закрыто |

## 1. Контекст и цель

Автомат платежа (4.1) двигают канонические события шлюза (4.3) и политика
завершения (4.5), но у состояний `created`/`pending` нет события-«будильника»:
истечение счета зависит только от времени (`expires_at` выдается мерчанту в ответе
на создание, `CBL-000` раздел 5). Без фоновой задачи счет с истекшим `expires_at`
остается в `created`/`pending` навсегда: мерчант не получает `payment.expired`
(4.7), сверка 9.x и отчетность видят вечно открытые счета.

Второй класс - зависшие платежи:

- `creating`: процесс 4.2 мог упасть между созданием записи и фиксацией котировки
  или счета в шлюзе; платеж навсегда остается в `creating`, а too-early события
  шлюза для него живут только до исчерпания retry-пауз (KI-payment-05);
- `detected`/`confirming` без движения: потерянное событие шлюза или долгий набор
  подтверждений; деньги могут быть в сети, автоматическая терминализация
  запрещена - нужен наблюдаемый статус (WARN, счетчики) и ремедиация через 4.4
  (после KI-01) и сверку 9.x.

Задача добавляет janitor: периодический проход, который (а) истекает счета
`created`/`pending` через предикат `ShouldExpire` (4.5), (б) детерминированно
закрывает зависшие `creating` состоянием `failed`, (в) делает зависшие
`detected`/`confirming` видимыми в логах, не меняя состояние и не трогая деньги.

## 2. Границы

In scope: janitor (usecase), выборки хранилища `FindExpired`/`FindCreating`/
`FindStuck`, частичный индекс для `creating` (миграция), конфигурация и обвязка
`main`, тесты unit/integration/e2e.

Out of scope: перепроверка `GetGatewayPayment` у шлюза (4.4, заблокирована KI-01);
публикация `payment.events` из переходов janitor (4.7 - переходы видны через
`payment_transitions`, outbox-запись добавит 4.7); сверка с Reconciler (9.x);
закрытие счета в шлюзе (счет истекает на стороне шлюза по переданному
`expires_at`, Connector 3.x); Prometheus-метрики (0.7).

## 3. Функциональные требования

FR-1. `usecase.Janitor` выполняет немедленный проход при старте, затем проходы
(`Sweep`) по расписанию `Run(ctx)`: тикер `PAYMENT_JANITOR_INTERVAL` (по умолчанию
30s; `0` - janitor выключен; невалидное значение или меньше 1s - отказ старта),
размер пакета выборок `PAYMENT_JANITOR_BATCH` (по умолчанию 100, диапазон
1 - 1000, невалидное значение - отказ старта; вместимость пакета обеспечена
хранилищем: фоновые выборки используют отдельный потолок 1000, не лимит
пользовательского списка 200). Проход возвращает
и вызывает логирование по счетчикам: `expired`, `creating_failed`, `stuck`,
`conflicts`, `errors`. Сводный лог - Info только при ненулевых эффектах,
сводка пустого прохода - Debug.

FR-2. Истечение: `FindExpired(now, batch)` возвращает `created`/`pending` с
`expires_at <= now`; для каждого платежа janitor повторно проверяет
`domain.ShouldExpire(state, expiresAt, now)` на снимке и выполняет
`Transition(id, state_version, expired, reason = "janitor expired")`. CAS по
`state_version` закрывает гонку с consumer/4.4/4.2: проигравший конфликт
(`domain.ErrStateConflict`) пропускается без ошибки и учитывается счетчиком
`conflicts`; повторный проход увидит актуальное состояние. Второй барьер БД
(матрица триггера) делает `detected -> expired` невозможным даже при ошибке в
коде (KI-payment-08).

FR-3. Зависшие создания: `FindCreating(now - PAYMENT_CREATING_TIMEOUT, batch)`
возвращает `creating`, созданные не позже порога; janitor закрывает их
`Transition(id, state_version, failed, reason = "janitor creating timeout")`.
`PAYMENT_CREATING_TIMEOUT` по умолчанию 5m (строгий разбор, минимум 1m: меньшее
значение массово закрывало бы живые создания 4.2 с дедлайном RPC 6 с).
Обоснование: штатное создание (4.2) укладывается в секунды;
`failed` делает too-early события для этого платежа детерминированно
устаревшими вместо бесконечных повторов (KI-payment-05). Возможный «осиротевший»
invoice в шлюзе без адреса у мерчанта неоплатим и истекает на стороне шлюза;
сверка 9.x его увидит как неоплаченный (фиксируется в KI-payment-09).

FR-4. Зависшие `detected`/`confirming`: `FindStuck(now - PAYMENT_STUCK_TIMEOUT,
batch)`; janitor только логирует WARN (до 10 платежей за проход с полным
`payment_id`, остальные - счетчиком) и учитывает их в `stuck`: автоматическая
терминализация денежного состояния недопустима (деньги в сети, T-01).
`PAYMENT_STUCK_TIMEOUT` по умолчанию 6h (строгий разбор, минимум 1m). Ремедиация:
4.4 после KI-01, сверка 9.x; вплоть до этого платёж не меняется. Смежный случай
(деньги в сети по уже истекшему счету) дополнительно выделен в consumer-е 4.3:
поздний `detected`/`confirmed` после `expired` пишет отдельный WARN
`late canonical event after expiry needs manual review` (алерт по логам до
метрик 0.7, KI-payment-08).

FR-5. Отказоустойчивость прохода: ошибка отдельного платежа (не конфликт) не
прерывает проход - платеж учитывается счетчиком `errors` с WARN-логом, проход
продолжается; ошибка выборки пропускает соответствующую секцию прохода
(`errors + 1`, WARN); отмена контекста (SIGTERM) прерывает проход между
платежами; janitor не возвращает ошибок наружу - наблюдаемость через логи,
после 0.7 - через метрики.

FR-6. Конфигурация и обвязка `main`: janitor стартует после применения миграций
при заданном `PG_DSN` (Kafka не требуется), работает в отдельной горутине до
завершения контекста; эффективная конфигурация (интервал, пакет, таймауты)
логируется при старте, при `PAYMENT_JANITOR_INTERVAL=0` - лог «janitor disabled».
Строгий разбор конфигурации: пустое значение - значение по умолчанию, невалидное,
отрицательное, вне диапазона или меньше минимума - отказ старта сервиса (опечатка
не должна молча отключать, ускорять фоновые переходы или массово закрывать живые
создания).

FR-7. Все времена - UTC; пороговые сравнения на границе включают равенство
(`expires_at == now` истекает; `created_at == now - timeout` - зависшее).

## 4. Контракты

- Внешние контракты не меняются: новых gRPC/REST/Kafka-топиков и схем нет;
  переходы janitor - обычные переходы автомата, наблюдаемые в
  `payment_transitions` (reason `janitor expired`/`janitor creating timeout`);
  состояние `expired` соответствует enum `PAYMENT_STATE_EXPIRED` (CF-1).
- Переменные окружения: `PAYMENT_JANITOR_INTERVAL` (duration, по умолчанию 30s,
  0 - выключен, минимум 1s), `PAYMENT_JANITOR_BATCH` (int, по умолчанию 100,
  1 - 1000), `PAYMENT_CREATING_TIMEOUT` (duration, по умолчанию 5m, минимум 1m),
  `PAYMENT_STUCK_TIMEOUT` (duration, по умолчанию 6h, минимум 1m).
- Хранилище: `FindCreating` (новая), `FindExpired`/`FindStuck` (4.1) поверх
  частичных индексов `payments_creating_idx`/`payments_expiry_idx`/
  `payments_stuck_idx`; фоновые выборки клампятся отдельным потолком 1000
  (`maxBackgroundLimit`), не лимитом пользовательского списка 200.

## 5. Модель данных и миграции

Миграция `00004_creating_idx.sql` (только вперед):
`CREATE INDEX payments_creating_idx ON payments (created_at) WHERE state = 'creating'`
(поиск зависших созданий без сканирования всей таблицы). Индексы для истечения
и зависших detected/confirming уже созданы в 00001. Существующие данные не
переписываются. `CREATE INDEX` без `CONCURRENTLY` берет краткую блокировку записи
`payments`: на текущем масштабе допустимо (стиль 00001), при росте таблицы
(KI-payment-02) - отдельная задача с `NO TRANSACTION`-миграцией.

## 6. Конечные автоматы и правила

Переходы janitor строго через матрицу 4.1 и `storage.Repository.Transition`
(CAS по `state_version`, row lock в транзакции, строка `payment_transitions`):

| Секция | Из | В | Условие | Reason |
| :-- | :-- | :-- | :-- | :-- |
| Истечение | created, pending | expired | `ShouldExpire` (4.5) | `janitor expired` |
| Зависшие | creating | failed | возраст > `PAYMENT_CREATING_TIMEOUT` | `janitor creating timeout` |
| Наблюдение | detected, confirming | - | возраст > `PAYMENT_STUCK_TIMEOUT` | WARN-лог, без перехода |

Терминальные состояния janitor не трогает; `expired` - терминальное.

## 7. Edge cases

`expires_at` NULL (не истекает); `expires_at` ровно `now` (истекает); снимок
`pending`, к моменту перехода уже `detected`/`completed` (CAS-конфликт либо
переход запрещен вторым барьером - пропуск без ошибки); повторный проход по
уже истекшему платежу (выборка по состоянию не вернет его); два экземпляра
janitor (CAS делает эффект однократным, лишние конфликты видны счетчиком);
`created_at` ровно на границе таймаута (считается зависшим); создание, у
которого 4.2 успел зафиксировать `quote_id`/`gateway_id`, но не довел до
`created` (закрывается `failed`, частичные данные не стираются); большой
backlog (пакет за проход, следующие тики доводят остаток); ошибка одного
перехода (проход продолжается); `stuck`-платежи настоящих сетей с легитимно
долгим набором подтверждений (порог 6h перекрывает типичные сети, это порог
алерта, а не решения); отмена контекста посреди прохода (ранний выход);
`errors` из-за невалидного состояния в БД (счетчик, лог, без перехода).

## 8. Нефункциональные требования

Один проход - не более трех выборок по частичным индексам и по одному UPDATE
на найденный платеж; внешних вызовов нет; конкурентность с consumer и gRPC -
через CAS без глобальных блокировок (T-PAY-02); пакетность ограничивает время
прохода и нагрузку на БД при распутывании backlog; N+1 отсутствует (переходы
пакетом последовательны по найденным строкам); логи не содержат сумм и
реквизитов, только payment_id, состояние, версию; интервалы и таймауты
валидируются при старте (FR-6); после 0.7 счетчики `expired`, `creating_failed`,
`stuck`, `conflicts`, `errors` публикуются Prometheus-метриками (точка
расширения - плейсхолдер `metricsHandler`).

## 11. Открытые вопросы и решения

- Поздний `detected` после `expired` (оплата пришла после истечения) остается
  ручным разбором: janitor лишь гарантирует, что истечение не переопределяет
  уже обнаруженную оплату (CAS + второй барьер); алерты - 9.x (KI-payment-08).
- Зависший `creating` закрывается `failed` без обращения к шлюзу: неоплаченный
  invoice без выданного мерчанту адреса не несет риска; возможное расхождение
  «invoice есть, платеж failed» - тема сверки 9.x (KI-payment-09).
- Автоматический перевод зависших `detected`/`confirming` в `failed` отклонен:
  деньги в сети, решение принимает сверка с шлюзом (T-01, 9.x), janitor
  ограничивается наблюдением.
- `created` живет до появления 4.2 (KI-01): до этого тикеты в `created` могут
  висеть до `expires_at`; это не ошибка janitor-а, а следствие отсутствия шага
  создания счета в шлюзе. Требование к 4.2: `expires_at` фиксируется не позже
  перехода `creating -> created` - иначе счет не истечет (ShouldExpire без
  срока всегда false) и зависнет до появления наблюдения в 9.x.
- Связь с 4.7: переходы janitor-а (expired/failed) должны попасть в
  `payment.events` через тот же outbox, что и переходы consumer-а; точка
  встраивания - единая запись в `Repository.TransitionTx` (acceptance-критерий
  задачи 4.7), иначе мерчант не получит `payment.expired` (8.x).

## 12. Ревью (CBL-001, шаг 6)

Четыре независимых прохода (15.10.2026). Блокеров нет. MAJOR закрыты:
пакет фоновых выборок резался потолком списка 200 против заявленных 1000
(введен `maxBackgroundLimit` 1000, интеграционный тест 205 строк при batch 250);
границы равенства FR-7 не были покрыты (unit-тесты `expires_at == now`,
`created_at == cutoff`, аргументы выборок, доменный кейс `ShouldExpire`);
AGENTS.md обновлен в этом коммите (T-PAY-06, env, KI-payment-05 переформулирован,
KI-payment-08 уточнен, KI-payment-09 добавлен, runbook, журнал); опечатка в env
могла ускорить фоновые переходы (минимумы интервала 1s, creating/stuck 1m,
строгий разбор batch); поздний `detected` после `expired` теперь отдельный WARN
`late canonical event after expiry needs manual review` (KI-payment-08).
MINOR закрыты: отмена контекста не шумит ошибками (ранний выход между секциями),
свежее создание в unit, `confirming` в интеграционном stuck-сценарии,
параллельные два janitor-а, `require.Len` перед индексацией, первый проход сразу
при старте, `CONCURRENTLY`-оговорка для prod, комментарий к 2s в compose.
Принято без изменений: отсутствие jitter у реплик (корректность держит CAS) и
`lock_timeout` для фоновых транзакций (пакет последователен, порог риска - 14.6).
